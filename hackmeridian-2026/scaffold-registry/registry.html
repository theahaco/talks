Stellar Registry

Name it. Publish it. Import it.

Scaffold runs your contract locally. The registry is how it gets to testnet: publish the Wasm, deploy it under a name, and anyone, your own app included, uses that name instead of a C… address.

  • Answer the question: Scaffold runs your contract locally; getting it onto testnet under a name is Registry's job.
  • And once it has a name, anyone can find it. You use other people's contracts by name the same way, with no copied addresses.

About 40s.

The big idea

Give your contract a name, not an address. Ship it to testnet, and let anyone use it by that name.

  • Read the line out.
  • A name instead of a C… address: the same name works on every network, and nothing gets pasted into your frontend.

About 10s.

Three things to remember

Wasm = published code

Reusable contract code under a name and a semantic version. Only its author can publish new versions.

unverified/guess-the-number@1.0.0

Contract = deployed instance

A live contract registered by name. The name resolves to its C… address.

No version: it's one address.

unverified/ = open to all

Anyone can publish here, no approval. Bare names on the main registry need a manager's OK.

Use this!

  • Wasm: published code, under a name and a version. Only its author can publish new versions.
  • Contract: a deployed instance. The name points to one address, so it has no version.
  • unverified/: the open channel, no approval needed. Use this!
  • Forgetting unverified/ is the most common error, so say it twice.

About 1 min.

Ship to testnet by name


stellar keys fund me --network testnet
stellar keys use me

stellar registry publish \
  --wasm target/stellar/testnet/guess_the_number.wasm \
  --wasm-name unverified/guess-the-number --binver 1.0.0

stellar registry deploy \
  --contract-name unverified/guess-the-number \
  --wasm-name unverified/guess-the-number --version 1.0.0 \
  -- --admin me                        # constructor args after --

stellar registry fetch-contract-id unverified/guess-the-number   # C… for scaffold.yml

The Wasm is what stellar scaffold build --compile-only wrote with STELLAR_NETWORK=testnet. Add --dry-run to preview any write.

  • Click through the highlights:
  • Fund your testnet account and make it the default.
  • Publish the Wasm Scaffold compiled, under a name and a version.
  • Deploy a named contract from it. Constructor arguments go after the --.
  • fetch-contract-id gives you the C… address you'll put in scaffold.yml.
  • Mention --dry-run to preview any write, and create-alias to call the contract by name from the CLI.

About 1:45.

How names are organised

One root registry, many sub-registries


registry          root: bare names, manager-approved
├── unverified/   open to anyone: use this!
├── oz/           OpenZeppelin Wasms, ready to deploy
├── circle/       circle/usdc
├── soroswap/     soroswap/router, soroswap/factory
├── blend/        blend/pool-factory-v2, …
└── defindex/     defindex/xlm-vault, …

A sub-registry is its own registry contract with its own rules, registered by name in the root. Names read <sub-registry>/<name>.

Sub-registries group related contracts under one prefix, like soroswap/router and soroswap/factory.

Browse them all at rgstry.xyz under Contracts.

  • Every name so far started with unverified/. That's a sub-registry: the open one.
  • The root registry holds bare names, like registry itself, and those need a manager's approval.
  • Other sub-registries group related contracts: oz for OpenZeppelin Wasms, circle/usdc, soroswap's router and factory, blend, defindex.
  • All of them are browsable at rgstry.xyz under Contracts.

Start from OpenZeppelin

Deploy OpenZeppelin straight from oz/


stellar registry deploy \
  --contract-name unverified/my-token \
  --wasm-name oz/ft-standard \
  -- --name "My Token" --symbol MTK --decimals 7 --owner me --initial_supply 1000000

Your name, their Wasm: deploy into unverified/ from any sub-registry. Want to edit the source instead? stellar scaffold generate contract --from oz/…

  • Need a token or an NFT? Don't write one.
  • oz/ has more than 30 prebuilt OpenZeppelin combinations on testnet and mainnet: fungible tokens with caps, pausing, allowlists or voting; NFTs with royalties or enumeration; vaults.
  • Deploy one under your own unverified/ name. Constructor args go after --, and deploy … -- --help lists them.
  • Want to change the source? Use Scaffold's generate --from oz/… instead.

Call any named contract from Rust

You already have: guess-the-number pays out with stellar_registry::import_asset!("xlm").


let game = stellar_registry::import_contract!(
    env, "unverified/guess-the-number");   // typed client, no address in source

let won = game.guess(&5, &player);
  

STELLAR_NETWORK=testnet stellar scaffold build   # names resolve at build time

Defaults to local, and switching networks rebuilds automatically. Assets like xlm resolve at runtime, so one Wasm works on any network. Contract names resolve at build time: after a redeploy, cargo clean and rebuild.

About 30s.

Registry survival kit

  • Auth failure on publish? You used a bare name. Add unverified/
  • Error(Contract, #5): that contract name is taken. #8: publish a higher --binver
  • Macro can't find a contract? STELLAR_NETWORK wasn't set at build time
  • deploy … -- --help prints the constructor's arguments
  • Teach your agent: Registry skill at skills.stellar.org
  • The errors people will actually hit:
  • Auth failure on publish: you used a bare name, so add unverified/.
  • Error #5: that contract name is taken. Error #8: publish a higher --binver.
  • Macro can't find a contract: STELLAR_NETWORK wasn't set when you built.
  • deploy … -- --help prints a contract's constructor arguments, and skills.stellar.org has the Registry skill for your coding agent.
